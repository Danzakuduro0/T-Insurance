# OpenAPI — первая половина шага 9

После обычного запуска backend:

- http://localhost:8080/swagger — Swagger UI, интерактивные запросы.
- http://localhost:8080/openapi.json — спецификация OpenAPI 3.1.0, импортируется в Postman и инструменты генерации клиентов.

UI и спецификация доступны без входа. Защищённые API по-прежнему требуют JWT и проверяют права. Спецификация содержит только описание API, без данных пользователей. JS/CSS Swagger UI поставляются внутри серверного JAR через WebJar, CDN и интернет при открытии страницы не нужны. Внешний validator отключён, токены не сохраняются между перезагрузками.

## Как проверить

1. Открыть /swagger, раскрыть POST /api/mobile/auth/login либо POST /api/operator/auth/login, нажать Try it out.
2. Для мобильного входа указать phone, password, device (installationId, platform). Для веб-входа — email и password. Демо-учётные записи описаны в README; нужны включённые демо-данные.
3. Выполнить запрос, скопировать accessToken из ответа.
4. Нажать Authorize: вставить токен без префикса Bearer в MobileBearer или OperatorBearer соответственно.
5. Выполнить нужный запрос. Для dashboard, списка операторов и назначения нужен веб-токен ADMIN.
6. После истечения accessToken вызвать refresh с refreshToken. Новый accessToken снова вставить в Authorize; refreshToken одноразовый. Swagger не делает обновление автоматически.

Try it out выполняет реальные операции с локальными вымышленными обращениями: отправку, замену файлов, отмену и другие действия.

## Контракт и архитектура

Пакет server/openapi: SchemaRegistry строит схемы из kotlinx.serialization-дескрипторов DTO; ApiDocument собирает структуру; AuthOperations, MobileOperations и OperatorOperations описывают методы, параметры и ответы; OpenApiRoutes отдаёт спецификацию и UI. Адреса берутся из существующих MobileApi/OperatorApi. DTO, runtime-маршруты и фронтенд не изменены.

Сохраняются обязательность полей, nullable, перечисления, массивы, int64 и свободный JSON. Правила, зависящие от состояния обращения и БД, описаны в операциях/профильных документах; комплектность и лимиты документов получаются через event-types. null в PATCH означает отсутствие изменения. Спецификация не подменяет серверную валидацию.

Для файла 422 возвращает ClaimFileDto, а не ErrorResponse. 204 не имеет тела. Частотное ограничение авторизации 429 может быть без JSON-тела; Retry-After указывает ожидание. Для загрузки используется multipart/form-data, для скачивания JPEG/PNG/PDF — двоичное содержимое. Два Bearer-канала нельзя взаимозаменять.

Новые DTO отражаются через сериализаторы; новые методы необходимо добавить в соответствующую группу операций. OpenApiTest проверяет совпадение путей/методов с маршрутами, уникальность operationId, ссылки схем, авторизацию и доступность UI-ресурсов. После теста документ также доступен в server/build/openapi.json. Полноту смысловых ограничений нужно проверять при изменении бизнес-правил.

S3 не входит в эту часть шага 9; хранение файлов осталось прежним. Текущий frontend MobileApiClient уже использует общие пути и DTO (включая уведомления); для Swagger изменений в frontend не требуется.
