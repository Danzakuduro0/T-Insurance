# Шаг 6: действия оператора

Все пути ниже начинаются с `/api/operator/claims/{id}`. Запросы защищены JWT оператора; ответы при успехе — `200` и обновлённый `ClaimCard`. DTO — `core/api/operator/OperatorActions.kt`, пути — `OperatorApi`.

| Метод и путь | Тело | Условия |
|---|---|---|
| POST `/request-materials` | `message`, `items` | Только назначенный оператор, IN_REVIEW → NEEDS_INFO |
| PUT `/review-result` | `summary`, `clientComment` | Только назначенный оператор, IN_REVIEW; сохраняет REVIEW_RESULT без смены статуса |
| POST `/complete` | Нет | Только назначенный оператор; IN_REVIEW → COMPLETED; нужен итог текущего раунда рассмотрения |
| POST `/cancel` | `reason`, `clientComment` | Назначенный оператор или администратор; разрешённые переходы проверяет FSM |

`summary` и `reason` — внутренние тексты. Клиент получает `message` запроса и `clientComment` при завершении/закрытии. Строки обязательны, после trim — 1–4000 символов. Итог описывает проверку материалов, а не выплату.

## Запрос уточнений

```json
{
  "message": "Уточните обстоятельства и приложите снимки",
  "items": [
    {"fieldName": "description", "comment": "Укажите, как появилось повреждение"},
    {"documentType": "DAMAGE_PHOTO", "minCount": 1, "comment": "Добавьте общий вид автомобиля"},
    {"documentType": "DAMAGE_PHOTO", "fileId": 42, "comment": "Замените этот снимок более чётким"}
  ]
}
```

- `fieldName` или `documentType`: ровно одно. Имена полей берутся из формы выбранного типа события. `fileId` относится к этому же обращению и типу документа.
- Без `fileId` количество `minCount` означает **новые принятые файлы после запроса**, старые фото не засчитываются. С `fileId` требуется замена именно этого файла через `replacesFileId`; `minCount = 1`.
- Для поля требуется ответ клиента через PATCH после запроса (можно подтвердить прежнее значение). Пустой ответ не засчитывается. Разрешено менять только запрошенные поля.
- 1–30 пунктов; дубли пунктов и запрос, превышающий лимит вложений, отклоняются с 400. Один файл не засчитывается одновременно как замена и дополнительное фото.
- Повторный submit без выполнения пунктов возвращает 409 и сохраняет запрос. После submit запрос остаётся OPEN до проверки фото. Если ML отверг новую фотографию, обращение возвращается в NEEDS_INFO с тем же запросом.
- Недоступность анализа не блокирует ручное рассмотрение: при принятом формате файла сохраняется существующий сценарий FAILED → ручная проверка.

## Итог и закрытие

```json
{"summary":"Материалы проверены специалистом","clientComment":"Рассмотрение материалов завершено"}
```

Повторное сохранение создаёт новое решение с `supersedesId`; прежний итог остаётся в истории. После нового раунда уточнений требуется новый итог. Повторное завершение или неподходящий статус — 409. Действие другого оператора — 403, клиентский токен — 401, чужой файл в запросе — 400 без раскрытия сведений о нём.

Закрытие без обработки требует отдельного текста для клиента и внутренней причины. Оператор может закрыть свои ASSIGNED, IN_REVIEW, NEEDS_INFO. Администратор дополнительно может закрыть QUEUED и IN_ANALYSIS. DRAFT сотрудникам недоступен. Закрытие отменяет открытый запрос уточнений.

При переходе в NEEDS_INFO, COMPLETED или CANCELLED освобождается активное место оператора; если автоназначение включено и оператор ONLINE, ему предлагается следующее обращение. Историческое назначение сохраняется в журнале. При повторном выходе в QUEUED старое назначение снимается, чтобы обращение оставалось доступным общей очереди; автоназначение может вернуть его прежнему оператору. Все записи действия и переход статуса выполняются в транзакции.

## Организация кода

- `operator/actions/OperatorActionRoutes` — HTTP.
- `operator/actions/OperatorActionsService` — транзакции действий, права, результат и переходы.
- `operator/actions/MaterialsRequestValidator` — проверка параметров запроса.
- `claims/ManualMaterialsRepository` — запись/поиск ручного запроса.
- `claims/ManualMaterialsChecker` — выполнение пунктов запроса при отправке и маршрутизации.
- `ClaimIntake`, `ClaimStatusService`, `ClaimDecisionWriter`, `AutoAssigner` — общие существующие компоненты.

Новые миграции не требуются: используется схема V7. Уведомления (шаг 7) пока не реализованы; клиент читает карточку и временную шкалу.

## Postman

Войдите оператором, возьмите обращение и начните рассмотрение. В отдельной папке «6. Действия оператора» укажите `actionClaimId`. По умолчанию запросы пропускаются в Runner, пока `runOperatorActions` не равен `true`. Запускайте действия по одному: запрос уточнений, завершение и отмена — разные ветви сценария. Для завершения сначала выполните PUT `/review-result`.
