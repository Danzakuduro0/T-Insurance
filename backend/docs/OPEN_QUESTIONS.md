# Ответы на вопросы и принятые решения (бэкенд)

Номера — из документа уточняющих вопросов, ответы получены. Здесь зафиксировано, как каждый ответ реализован
в бэкенде или в каком шаге будет реализован. Значения, которые ответы оставили на усмотрение команды, вынесены
в настройки (`server/src/main/resources/application.yaml`) или справочники БД, чтобы их можно было менять без
правки логики. Справочники меняются новой миграцией Flyway; старые миграции не правим.

| 7 | Поля и документы зависят от типа, правила хранятся в справочнике | `event_type_fields` (CORE — поля обращения, DETAIL — ключи в `claims.event_details`). Форма для клиента — `GET /api/mobile/event-types` |

| 19, 23 | Минимум — качество и наличие повреждения; оператору — значение, уверенность и признаки | `image_analyses`: `damage_detected`, `car_part`, `damage_area`. В карточке оператора — анализ по каждому фото |
| 25 | Направления: обычная обработка, запрос материалов, ручная проверка | Направления `STANDARD` и `MANUAL_REVIEW`; «запрос материалов» — статус `NEEDS_INFO` |
| 27 | Обычный, повышенный, высокий | Приоритет 1..3 (CHECK в БД) |
| 31, 32 | Базовый маршрут статусов; администратор исправляет ошибочное состояние с записью в журнал | 9 статусов: «проверка комплектности» = `IN_ANALYSIS`, «закрыто без обработки» = `CANCELLED`. Закрыть может сотрудник; у администратора есть корректирующие переходы. Причина обязательна (CHECK в БД + проверка в коде) |
| 34 | Хранить время входа в статус, подсвечивать превышение; пороги в настройках | `claims.status_changed_at`, сроки в `claim_statuses.sla_hours`; в очереди и карточке — `dueAt`, `isOverdue` |
| 35 | Что видно в карточке | Клиент, договор, событие и доп. сведения, участники, документы со статусом анализа, проверки, приоритет, назначенный, история |
| 36, 37, 38 | Оператор подтверждает или исправляет; исходное значение сохраняется; причина нужна при исправлении | Шаг 4: `POST /api/operator/claims/{id}/decisions/confirm` (CONFIRM, без причины) и `/override` (OVERRIDE с обязательной причиной) для вида повреждения, направления и приоритета. Исходное решение остаётся в карточке (`isCurrent = false`, ссылка `supersedesId`), в журнале — старое и новое значение и причина. Менять может оператор, которому назначено обращение, или администратор. Вид `REVIEW_RESULT` — итог рассмотрения (шаг 6, не решение о выплате) |
| 24, 26 | Порог настраиваемый и обоснованный; приоритет по типу, полноте, ожиданию; оператор может изменить с причиной | Порог `routing.confidenceThreshold` (0.65) в настройках, правила маршрутизации — `RoutingRules` с причинами в решении; оператор исправляет направление и приоритет с причиной (шаг 4) |
| 39, 40 | Фильтры: статус, приоритет, дата создания, тип случая, сотрудник; поиск по номеру и договору | `GET /api/operator/queue`: `status`, `minPriority`, `createdFrom/To`, `eventType`, `assigned`/`assignedTo`, `direction`, `overdue`, `manualReview`, `search` |
| 42 | Старое и новое значение, источник, время; комментарий при отмене автоматического решения | `audit_log` и `claim_decisions` |
| 44 | Каналы кроме центра уведомлений — имитация | В `notifications.channel` добавлен SMS |
| 52 | Тестовые пользователи и роли, права на каждое действие | JWT, роли клиент / оператор / администратор |
| 14, 16, 17 | Лимиты файлов — на усмотрение команды; битый файл отклонить сразу и предложить замену; дубли по контрольной сумме | Шаг 2: формат проверяется по содержимому (JPEG, PNG, PDF), размер файла — из `document_types`, до 15 файлов и 100 МБ на обращение (`files.*` в настройках). Непригодный файл → 422 с причиной и подсказкой, остальные материалы сохраняются; замена через `replacesFileId`. Дубли — по SHA-256 в обращении; то же фото в другом обращении (точная копия или пересжатая/уменьшенная — по перцептивному хэшу `phash`) помечает его для проверки: оператор видит в карточке `foundInOtherClaim`, клиенту это не показывается |
| 18 | Обезличенные изображения | Из фото удаляются метаданные (EXIF с геолокацией, модель телефона); ориентация снимка сохраняется |

## Будет реализовано в следующих шагах

| № | Ответ (кратко) | Шаг |
|---|---|---|
| 18 | Использовать заранее обезличенные изображения | Данные от ML-инженера |
| 21, 22, 50, 51 | Проверка формата сразу, анализ в фоне; при плохом фото — запрос переснять с подсказкой; если ML недоступен — обращение не ждёт, оператор видит «анализ не завершён» | Шаг 3: фото анализируется в фоне сразу после загрузки (ML-сервис по `ML_URL` или локальная проверка качества); непригодное фото, пока его можно заменить, отклоняется с подсказкой по конкретной проблеме; после отправки обращение ждёт анализ (не дольше 15 мин) и уходит в очередь; ML недоступен — 3 повтора (30/90/270 с), потом `analysis_status = FAILED` и ручная проверка |
| 28, 29 | Предпочтительно автоназначение свободному подходящему оператору с ручным переназначением; защита от двойного захвата | 5 — автоназначение |
| 33 | После дозагрузки — на проверку комплектности, затем к назначенному оператору; правило единое | 3–5: повторная проверка уже есть; возврат к прежнему оператору — в шаге 5 |
| 36, 41 | Действия оператора; журнал приоритета, направления, назначения, документов, уведомлений | 6 — действия оператора |
| 43, 44 | Обязательный центр уведомлений; события: отправлено, нужны материалы, материалы получены, завершено | 7 — уведомления |
| 30, 45–48 | Администратор: перегрузка (предупредить, предложить перераспределение, не повышать приоритет всем), показатели, переназначение | 8 — администратор |
| 3, 53 | Учебный профиль нагрузки, цели по времени ответа, небольшой нагрузочный тест | 10 — нагрузка и демо |
| 49 | Изображения — желательно S3-совместимое хранилище | 9 — реализация `FileStorage` под S3 |
