# Контракт «бэкенд ↔ ML-сервис анализа фото» — черновик для согласования

Статус: **предложение бэкенда**, ждёт подтверждения ML-инженера. Всё, что помечено «❓», ML-инженер подтверждает или меняет.
Классы, проблемы качества, формат ответа и повторы взяты из раздела 6 «Детализации требований». Отличия от документа
предлагает бэкенд — они перечислены в конце.
Без ML_URL бэкенд работает с локальной проверкой качества (размытость, яркость, разрешение по порогам 6.3); вид повреждения она не определяет, поэтому такие обращения идут на ручную проверку.

## Как устроено

```
клиент загрузил фото → сервер проверил формат, сохранил → задача ANALYZE_IMAGE в очереди
                                                              │
                                    фоновый воркер бэкенда ───┘
                                              │  POST /analyze (storage_key)
                                              ▼
                                         ML-сервис ── ответ JSON ──▶ image_analyses, claim_files.analysis_status
```

- ML-сервис вызывается только из фонового воркера, поэтому обращение не ждёт ответа модели (вопрос 51).
- ML-сервис не знает ничего о клиенте: он получает только картинку и тип документа, без ФИО, телефона и номера полиса.
- Если ML-сервис недоступен, воркер повторяет запрос, а потом отправляет обращение оператору с пометкой «анализ не завершён» (вопрос 22).

## Запрос (реализовано в бэкенде, шаг 3)

`POST {ML_URL}/analyze`, `application/json` — как в разделе 6.2 документа:

```json
{
  "document_id": "42",
  "claim_id": "8",
  "storage_key": "claims/8/0b1c…e9.jpg",
  "model_version": "latest",
  "document_type": "DAMAGE_PHOTO",
  "event_type": "CAR_GLASS"
}
```

- `document_id` и `claim_id` — числа в виде строк (в бэкенде id числовые, не UUID).
- `document_type`, `event_type` — дополнительные поля, их можно не использовать.
- **Как сервис читает файл.** S3 пока нет: в Docker Compose ML-контейнеру подключается та же папка с файлами, что у сервера, только на чтение (`/data/files`). Путь к фото: `/data/files/{storage_key}`. Когда появится S3, `storage_key` станет ключом в бакете.
- **Какое фото лежит в хранилище:**
  - без EXIF и геолокации;
  - ориентация снимка сохранена в EXIF Orientation — её нужно учитывать при чтении;
  - лица и номера скрыты заранее (раздел 6.6).

## Ответ `200 OK`

Формат — как в разделе 6.2 документа. Необязательные поля, которые бэкенд тоже сохранит, отмечены ниже.

```json
{
  "document_id": "42",
  "quality": { "score": 0.82, "acceptable": true, "issues": [] },
  "damage": {
    "type": "DENT",
    "confidence": 0.71,
    "top_classes": [
      { "label": "DENT", "confidence": 0.71 },
      { "label": "SCRATCH", "confidence": 0.18 }
    ],
    "car_part": "FRONT_BUMPER",
    "area": { "x": 0.12, "y": 0.40, "w": 0.30, "h": 0.22 }
  },
  "model_version": "v1.2.0",
  "processing_ms": 340
}
```

Если качество неприемлемо: `"quality": {"acceptable": false, "issues": ["BLURRY", "LOW_LIGHT"]}`, `"damage": null`.

| Поле | Обязательно | Значение | Куда пишет бэкенд |
|---|---|---|---|
| `model_version` | да | Версия модели; решения системы ссылаются на неё | `image_analyses.model_version` |
| `quality.acceptable` | да | Годится ли снимок | `quality_ok` |
| `quality.score` | да | 0…1 | `quality_score` |
| `quality.issues` | да (может быть пустым) | Коды из справочника ниже | `quality_issues` |
| `damage` | да (`null`, если качество плохое) | — | — |
| `damage.type` | да | Класс повреждения | `damage_type` |
| `damage.confidence` | да | 0…1; сравнивается с порогом маршрутизации | `damage_confidence` |
| `damage.top_classes` | нет | Альтернативы для оператора | `raw_result` |
| `damage.car_part` | нет (рекомендуется, вопрос 19) | Часть автомобиля | `car_part` |
| `damage.area` | нет | Рамка повреждения: доли 0…1 от левого верхнего угла повёрнутого снимка | `damage_area` |
| `processing_ms` | нет | Время анализа | `raw_result` |

Наличие повреждения (обязательный минимум, вопрос 19): `damage` не `null` и в `quality.issues` нет `NO_DAMAGE_VISIBLE`.
Весь ответ сохраняется в `image_analyses.raw_result`, поэтому дополнительные поля ничего не ломают.

## Справочники (раздел 6 документа)

| Справочник | Значения |
|---|---|
| `damage.type` | `SCRATCH`, `DENT`, `BROKEN_GLASS`, `BUMPER_DAMAGE`, `HEADLIGHT_DAMAGE` |
| `quality.issues` | `BLURRY` (дисперсия Лапласа < 100), `LOW_LIGHT` (яркость < 40), `OVEREXPOSED` (> 230), `LOW_RESOLUTION` (меньшая сторона < 480 px), `NO_DAMAGE_VISIBLE` |
| `damage.car_part` ❓ | `FRONT_BUMPER`, `REAR_BUMPER`, `HOOD`, `TRUNK`, `DOOR`, `FENDER`, `WINDSHIELD`, `SIDE_WINDOW`, `HEADLIGHT`, `TAILLIGHT`, `MIRROR`, `WHEEL`, `ROOF`, `OTHER` |

По кодам `quality.issues` клиент получает подсказку, что переснять. Например, `BLURRY` → «Держите телефон неподвижно, снимок размыт». Тексты подсказок хранит бэкенд.

## Ошибки

| Ответ ML-сервиса | Что делает бэкенд |
|---|---|
| `422` с телом анализа (`quality.acceptable = false`) — как в документе | Сохраняет результат: фото непригодно |
| `422` без тела анализа / `400` — картинку не удалось разобрать | Повторов нет, анализ — `FAILED`, оператор смотрит фото сам |
| `429` / `503` — перегружен | Повтор с паузами 30 / 90 / 270 с. Заголовок `Retry-After` пока не учитывается |
| `5xx`, обрыв, нет ответа за **10 с** (п. 6.5) | До 3 повторов с паузами 30 / 90 / 270 с. Потом `FAILED` — оператор видит «Автоматический анализ недоступен» и продолжает вручную |

Тело ошибки: `{"error": "CODE", "message": "текст для логов"}`.

## Служебное

- `GET {ML_URL}/health` → `{"status": "UP", "model_version": "v1.2.0"}`. Предлагаемый контракт проверки доступности; опрос этого эндпоинта бэкендом пока не реализован.
- Бэкенд одновременно отправляет не больше **4** ❓ запросов; число задаётся в настройках.
- Адрес сервиса задаётся переменной `ML_URL`. Если она пустая, работает локальная заглушка. Так бэкенд, тесты и демо работают без ML.

## Что решает не ML

- **Порог «сомнительного» (вопрос 24, п. 6.4)** задаётся в настройках бэкенда: `routing.confidenceThreshold: 0.65`. Его можно менять без новой модели. От ML нужно обоснование на проверочной выборке (не меньше 20 изображений CarDD).
- **Маршрутизацию, приоритет и запрос «переснять»** выполняют правила бэкенда по ответу модели. Модель ничего не решает о выплате.

## Чем предложение бэкенда отличается от раздела 6 документа

| В документе | Предложение | Почему |
|---|---|---|
| Плохое качество — ответ `422` | Лучше `200` с `acceptable: false` | Это результат анализа, а не ошибка. Но бэкенд примет и `422` с телом |
| — | Дополнительно `car_part`, `area` | Вопрос 19: часть автомобиля рекомендуется, рамка помогает оператору |

## Вопросы ML-инженеру

1. Подходит ли формат запроса и ответа? Если нет — что поменять.
2. Справочник `car_part`: будет ли он (вопрос 19)?
3. Рекомендуемый порог уверенности и его обоснование (вопрос 24).
4. Размер изображения на входе модели: присылать 2048 px или меньше?
5. Сколько занимает анализ одного фото и сколько запросов сервис выдерживает одновременно? От этого зависят таймаут и лимит параллельных запросов.
6. Обезличивание (вопрос 18): ответ был «использовать заранее обезличенные изображения». Это значит, что сервис лица и номера не ищет и не замазывает, а демо-данные уже обезличены? Если сервис всё же должен это делать — нужно поле `privacy` в ответе и обезличенная копия снимка.
7. Как сервис будет запускаться на демо: Docker-образ в нашем `docker-compose.yml` или отдельный адрес?
